# 蜂鸣器接线与持续鸣叫排查

## 已有接线记录

依据 2026-11-22 晚间接线对话及用户上传的模块近照：模块型号为 **MH-FMD**，丝印明确写着 **低电平触发**，接口为 `GND / I/O / VCC`。

此前确定的接法如下；这是接线记录，不代表已经通过电气测量核验当前每根线的位置。

| 模块接口 | 树莓派物理针脚 | 功能 |
| --- | --- | --- |
| GND | 第 9 脚 | 地；原计划第 6 脚已被占用，后改用第 9 脚 |
| I/O | 第 11 脚 | BCM GPIO17 |
| VCC | 第 17 脚 | 3.3V；原计划第 1 脚已被占用，后改用第 17 脚 |

**物理第 17 脚是电源；GPIO17 位于物理第 11 脚。二者不能混淆。** 不按线的颜色推断接口。

## 持续鸣叫的已知情况

- 用户确认声音来自右下角接红、白、黑三根线的模块。
- 网页关闭蜂鸣器后，用户反馈实体仍响。
- 当前主程序使用 `Buzzer(mock=True)`；`control/buzzer.py` 没有真实 GPIO 驱动，所以网页关闭按钮尚不能改变实体引脚电平。
- 模块为低电平触发：正常连接时，I/O 低电平鸣叫，高电平关闭。输入悬空不能作为可靠的关闭方式。
- 这些证据尚不能断定接错线、模块故障，或确认持续鸣叫的唯一原因。

## 下一步

1. 树莓派联网后，先读取 GPIO17 状态并检查 GPIO 使用进程。
2. 按上述已知接线，确认没有其他驱动占用后，仅将 GPIO17 设为高电平关闭，现场确认声音是否停止；不扫描或切换其他未知 GPIO。
3. 关断测试后，再部署支持低电平触发的真实驱动，初始化和退出均明确输出关闭电平，验证网页开关与实物同步。
4. 若输出高电平仍响，关机断电后核对实际插针位置与模块接口，继续排查供电或接线。

最初重连 `192.168.111.233` 时 SSH 超时，随后在用户再次要求尝试时已恢复连接。执行前读取结果为 `GPIO17 = input`，下拉配置、读到高电平；`fuser` 未报告 GPIO 设备占用进程。随后仅执行 `pinctrl -e set 17 op pn dh`，命令成功，复读结果为 `GPIO17 = output`、高电平。**用户已现场确认“已经停止”**。由此验证了这组接线可用高电平消音；此前输入读取也为高，不能简单断定原来是持续逻辑低电平，未核实弱电平与实际电压。

这次手动操作不保证重启后保持设置。如需立即停止声音，应先正常关机并断开电源，再拔掉蜂鸣器 VCC，避免带电换线。

## 已完成的本地驱动，待板端部署

- `control/buzzer.py`：通过官方 libgpiod Python 绑定独占请求 GPIO17；仅接受已验证接线对应的 Pi 4 GPIO 芯片。请求时设置低电平有效、上拉、初始逻辑关闭（物理高电平）。申请失败会报错，不伪装为硬件模式成功。
- `main.py`：在模型初始化前创建蜂鸣器；每次启动默认关闭提醒，需网页主动开启。关闭提醒后停止输出，退出时再次明确写关闭值并释放 GPIO。即使关闭蜂鸣器报错，仍继续保存会话和释放摄像头。
- 网页分别标识蜂鸣器与灯的模式，避免真实蜂鸣器启用后把模拟灯误标成实物。
- `requirements-pi.txt` / `.lock`：加入 `gpiod==2.6.0`，锁定板端 CPython 3.11 / aarch64 wheel 哈希。
- `deploy/smart-desk-buzzer.conf`：仅在上述接线的设备上安装的用户服务配置，选择真实蜂鸣器模式；普通桌面运行继续默认模拟。

初始化与状态定义参照 [libgpiod LineSettings 官方说明](https://libgpiod.readthedocs.io/en/master/python_line_settings.html)。

本地 Python 共 34 项回归通过，覆盖初始关闭、低电平极性、开关门控、禁用时停声、退出释放、异常清理、GPIO 占用和错误芯片拒绝等；前端行为检查通过，覆盖真实蜂鸣器与模拟灯的独立标识。
